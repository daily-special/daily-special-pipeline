# 코드 규약 — daily-special-pipeline

> 이 문서는 이 저장소에서 코드를 쓰는 사람과 AI 모두를 **강제**한다.
> 어긋나는 코드는 리뷰가 아니라 규약 위반으로 다룬다. 규약을 바꿔야 한다면 코드가 아니라 이 문서를 먼저 고친다.
>
> 저장소 문서는 외부(위키·Notion)를 참조하지 않는다. 근거가 필요한 대목은 여기에 요약해 옮겨 적는다.
> 최종 수정: 2026-07-25

---

## 1. 아키텍처 — 헥사고날 Lite

의존은 **바깥에서 안으로만** 흐른다.

```
adapter  →  application  →  domain
                 ↑
              common (어디서나 import 가능, 아무것도 import 안 함)
```

### 폴더 구조

```
src/daily_special/
├── domain/          순수. 페르소나·요리·재료·만족도 엔진
│                    외부 라이브러리는 pydantic 외 금지
├── application/
│   ├── port/        Protocol 정의 (LlmPort, ExporterPort)
│   └── service/     생성·검증·재생성 루프. 프롬프트 조립
├── adapter/
│   ├── inbound/cli/     Typer CLI
│   └── outbound/
│       ├── llm/         OpenAI 어댑터 + 가짜 어댑터
│       └── export/      JSON 패키지 출력
└── common/          ids · errors · config

data/project_bible.json    게임 수치·어휘를 소유하는 설정 데이터
out/                       생성 산출물 (git에 커밋한다 — 3절)
tests/
docs/
```

`inbound` / `outbound`를 쓴다. `in`은 파이썬 예약어라 패키지명으로 못 쓴다.

### 경계는 사람이 아니라 도구가 지킨다

`import-linter`로 다음을 검사하고, CI 게이트에 포함한다.

- `domain` → `application`, `adapter` import **0**
- `application` → `adapter` import **0**
- `common` → 나머지 전부 import **0**

규약을 주석으로 적어두면 반드시 새어나간다. 계층 위반은 테스트 실패로 나타나야 한다.

### 이 구조를 쓰는 이유

이 파이프라인의 정체성은 "교체 가능한 외부 인프라(LLM API) + 순수한 게임 규칙"이다. 만족도 엔진은 LLM을 몰라야 하고, LLM 어댑터는 게임 규칙을 몰라야 한다. 포트/어댑터 어휘가 그 의도를 가장 직접적으로 드러낸다.

## 2. 도메인 표현 — Pydantic BaseModel

도메인 엔티티는 `dataclass`가 아니라 **Pydantic BaseModel**로 쓴다.

- 생성 시점에 검증이 걸려 **잘못된 상태의 객체가 태어나지 못한다**
- 불변식은 손수 쓴 `if`가 아니라 `field_validator` / `model_validator`로 선언한다

**규율 하나를 함께 강제한다 — 도메인의 Pydantic ≠ 출력 DTO의 Pydantic.**

도메인 엔티티는 게임 규칙 불변식만 담는다. 출력 JSON의 모양은 `adapter/outbound/export`의 별도 모델이 담는다. 하나로 겸하면 출력 포맷을 바꿀 때 도메인이 흔들린다.

pydantic은 웹·ORM 프레임워크가 아니라 값 검증 라이브러리다. domain에서 허용하는 유일한 외부 의존이다.

## 3. 변동 축과 안정 축

**이 파이프라인의 가장 중요한 규칙이다.**

일반 백엔드에서 스키마 변경 비용은 `코드 + 마이그레이션`이다. LLM 파이프라인에서는 여기에 **프롬프트 + 검증 규칙**이 더 붙는다. 스키마가 프롬프트에도 새어 들어가기 때문이다. **스키마의 소비자가 코드와 프롬프트, 둘이다.** 그래서 변동이 예상되는 축을 코드로 조여두면 변경 비용을 두 배로 낸다.

### 규칙 3-1. 게임 수치와 어휘는 ProjectBible이 소유한다

욕구 종류, 파라미터 축 이름과 범위, 요리 태그, 식이 제약 목록, 수량 — 전부 `data/project_bible.json`이 소유한다. 코드에 박지 않는다.

```python
# ❌ 게임 수치가 코드에 박힌 형태
class Persona(BaseModel):
    heat_ideal_min: int = Field(ge=0, le=100)
    seasoning_ideal_min: int = Field(ge=0, le=100)
    # 축이 하나 늘면 모델·프롬프트·검증이 전부 바뀐다

# ✅ 축을 분리한 형태
class AxisSpec(BaseModel):          # 설정 스키마는 오히려 강하게 조인다
    key: str
    label: str
    slider_min: int
    slider_max: int

class ProjectBible(BaseModel):
    axes: list[AxisSpec]
    needs: list[NeedSpec]

class Persona(BaseModel):           # 생성물 스키마는 느슨하게
    ideal_ranges: dict[str, IdealRange]   # key 집합은 ProjectBible.axes가 정의

    def check(self, bible: ProjectBible) -> list[Issue]: ...
```

실익은 **프롬프트가 같은 설정에서 생성된다**는 점이다.

```python
axis_lines = "\n".join(
    f"- {a.key} ({a.label}): {a.slider_min}~{a.slider_max}" for a in bible.axes
)
```

축이 3개에서 4개가 되어도 바뀌는 것은 설정 데이터뿐이다. 스키마와 프롬프트가 따로 노는 드리프트가 구조적으로 발생하지 않는다.

**대가**: 생성물 층은 `dict` 안까지 mypy가 못 들어간다. 그래서 **검증 책임이 ProjectBible로 이동한다** — 설정 스키마는 평소보다 강하게 조이고, 설정의 불변식 위반은 `list[Issue]`가 아니라 **생성 시점 예외**로 막는다. 설정이 틀리면 파이프라인 전 구간이 조용히 틀린 채로 통과한다.

### 규칙 3-2. 한 필드가 두 의미를 겸하지 않는다

규칙 3-1의 전제("소비자가 둘")에서 곧바로 따라 나온다. 한 필드가 두 의미를 겸하면 **한쪽 소비자에게는 맞고 다른 쪽에는 틀린 정보**가 된다.

우리 취향 3축이 정확히 이 함정 위에 있다. `min`/`max` 하나로 두면 코드에게는 "유효성 상한"이지만 프롬프트에게는 "이 값을 어디쯤에 넣어라"로 읽힌다. 실제 의미는 셋이다.

```python
# 의미가 다르면 필드도 다르다
slider_min: int
slider_max: int
"""플레이어가 조작할 수 있는 슬라이더 전체 범위."""

ideal_min: int
ideal_max: int
"""이 손님이 만족하는 구간. slider 범위보다 반드시 좁다."""

tolerance: int
"""ideal 구간을 벗어났을 때 만족도가 0이 되기까지의 여유."""
```

**증상으로 구별하는 법**: 생성 결과가 기술적으로는 유효한데 쓸모없다면, 검증을 조이기 전에 **필드가 두 가지를 말하고 있지 않은지** 본다. 그 경우 잘못은 모델이 아니라 스키마에 있다.

### 규칙 3-3. 산출물은 의미 기반 키로 참조한다

생성물이 상위 시스템의 내부 식별자(DB PK, 게임 내부 상수)에 결합하면, 그 식별자가 바뀔 때 검수한 결과까지 버려진다. 대사 트리거는 `situation: "dish_served_satisfied"` 같은 의미 키로 둔다. 상세는 `data-contract.md`.

## 4. LLM 연동

### 4-1. 프레임워크를 쓰지 않는다

LangChain·LangGraph를 도입하지 않는다. OpenAI SDK를 직접 쓴다.

판단 축은 "편한가"가 아니라 **에이전트인가 파이프라인인가**다. 그래프 프레임워크의 값어치는 분기가 런타임에 결정될 때 나온다. 우리는 그렇지 않다.

- 다음 행동을 정하는 주체가 **코드**다. 생성 → 검증 → 재생성 → 검토 → 출력 순서가 설계 시점에 고정돼 있다
- LLM이 도구를 고르지 않는다. 구조화 출력 하나만 뱉는다
- 오프라인 배치다. 죽으면 다시 돌리면 된다. 내구성 있는 재개가 필요 없다
- 오케스트레이터 프레임워크는 포트 뒤에 숨지 않고 `application` 자리를 차지한다. 헥사고날 규율과 둘 중 하나는 진다
- 구조화 출력은 SDK가 Pydantic 모델을 그대로 받아 처리한다. 출력 파서 계층이 얻는 게 없다

**넣는 비용 < 빼는 비용**이므로 늦게 결정하는 쪽이 싸다. 아래 조건이 하나라도 생기면 재검토한다.

1. LLM이 동적으로 도구를 선택해야 할 때
2. 분기·병렬이 늘어 직접 짠 오케스트레이션이 읽기 어려워질 때
3. 프로세스 재시작을 넘는 내구성 있는 재개가 필요할 때

### 4-2. LLM 포트는 범용으로 둔다

헥사고날에서 포트는 도메인 언어로 말하는 것이 정석이지만, **LLM 포트는 예외로 둔다.**

```python
# ✅ 범용 포트
class LlmPort(Protocol):
    async def generate(
        self, *, instruction: str, context: str, schema: type[T], tier: Tier
    ) -> T: ...

# ❌ 도메인 언어 포트 — 여기선 함정
class LlmPort(Protocol):
    async def generate_guests(self, bible: ProjectBible) -> list[Persona]: ...
```

아래를 고르면 **프롬프트가 어댑터 안으로 들어간다.** 그런데 프롬프트는 인프라 지식이 아니라 도메인 지식이다 — 어떤 손님을 원하는지, 무엇을 피해야 하는지는 어느 LLM 회사를 쓰는지와 무관하다. 프롬프트가 어댑터에 있으면 프로바이더 교체 시 프롬프트까지 다시 쓰게 되고 격리의 목적이 무너진다.

**프롬프트 조립은 `application`에 남는다.** 어댑터는 "이 스키마로 구조화 출력을 받아온다" 하나만 한다. 생성 작업이 늘어도 포트를 늘리지 않는다.

OpenAI 고유의 타입·예외·개념은 어댑터 안에서 끝낸다. 이것이 새면 격리가 무의미해진다.

### 4-3. 모델은 티어로 말한다

`application`은 모델명을 모른다. `QUALITY` / `FAST` 두 티어만 안다. 티어 → 모델 ID 변환은 어댑터가 한다.

- `QUALITY` — 페르소나·요리 생성처럼 품질이 눈에 보이는 곳
- `FAST` — 검토·판정처럼 창작이 아니라 비교만 하는 곳

**모델 ID는 티어까지 명시해 고정한다.** 세대 별칭에 의존하면 일상적인 호출이 조용히 가장 비싼 티어로 갈 수 있다.

**추론량(reasoning effort)도 티어 표에 함께 둔다.** 요즘 모델은 추론량이 모델 선택이 아니라 다이얼이라 같은 모델 ID로 세기만 바꿀 수 있다. 그렇다고 `application`이 그것을 정하게 두면 티어 추상화가 새고, 다이얼을 조정할 때마다 서비스 코드를 고치게 된다. 모델 선택과 같은 성격이므로 같은 자리에 둔다.

추론량을 정하는 기준은 **규칙으로 잡을 수 없는 것이 있는가**다. 스키마와 규칙 검증이 공짜로 막아주는 것에는 추론이 필요 없다. 배치 안에서 서로 겹치지 않는 것, 사연과 수치가 앞뒤로 맞는 것처럼 검증기가 판정할 수 없는 것에만 값이 있다. 그런 것이 없는 판정 작업은 0으로 둔다.

### 4-4. 구조화 출력

OpenAI `.parse()`로 받는다. strict 모드가 임의 키 dict를 금지하므로, 규칙 3-1의 느슨한 층은 **ProjectBible에서 스키마를 동적 생성**해 해결한다 — 축 하나가 필드 하나, 어휘가 enum이 된다.

수치 제약(`minimum`/`maximum`/`minItems`)은 strict 모드에서 거부될 수 있다. 제약은 **필드 설명으로 모델에 알리고**, 실제 강제는 `check()`가 한다.

## 5. 검증과 재생성

### 5-1. 검사는 싼 것부터 층으로 쌓는다

```
1층  스키마      어휘 밖의 값을 구조적으로 낼 수 없게 한다   비용 0
2층  규칙 검증   범위·중복·금칙어. 코드가 판정한다           비용 0
3층  의미 검토   LLM 호출                                    비용 있음
```

**규칙이 깨진 생성물은 3층에 넘기지 않는다.** 어차피 다시 만들 것이라 호출만 낭비된다.

### 5-2. 검증은 예외가 아니라 `list[Issue]`로 모아 돌려준다

첫 위반에서 예외를 던지면 재생성 피드백에 한 줄밖에 못 싣는다. 전부 모아야 한 번의 재생성으로 고칠 수 있다.

```python
class Issue(BaseModel):
    severity: Severity      # ERROR | WARNING
    field: str
    message: str            # 한국어. 그대로 재생성 프롬프트에 들어간다
```

예외는 **설정(ProjectBible)의 불변식 위반**에만 쓴다 (3-1 참조).

### 5-3. 재시도는 두 층으로 나눈다

- **어댑터** — 전송 실패만. 네트워크·rate limit, 지수 백오프
- **서비스** — 검증 실패로 인한 재생성. `Issue` 목록을 피드백으로 실어 **최대 3회**

한 곳에 두면 LLM 호출 횟수를 추적할 수 없게 된다.

**3회를 소진해도 생성물을 버리지 않는다.** 경고를 붙여 내보낸다. 검토 계층이 실패해도 마찬가지다 — 검토는 보조 장치이고, 여기서 예외를 올리면 이미 만들어진 멀쩡한 생성물까지 잃는다.

### 5-4. 자동 컷에는 근거가 있어야 한다

점수 임계값으로 자동 재생성을 걸지 않는다. 몇 점이 "너무 비슷한가"는 생성물이 충분히 쌓여야 알 수 있고, 근거 없는 컷은 멀쩡한 생성물을 버린다. 재생성은 돈과 시간을 쓰므로 잘못된 컷은 그대로 손해다.

점수는 **설명 용도**로 남긴다("어느 축이 얼마나 겹치는가"). 판정은 LLM 의미 검토가 한다.

## 6. 테스트

- **가짜 어댑터로 API 키 없이 전부 통과해야 한다.** 실호출 테스트는 별도 마커로 분리하고 기본 실행에서 제외한다
- **설계 결정은 주석이 아니라 테스트로 고정한다.** "만족도는 곱셈이다"는 주석이 아니라 "한 축이 0이면 전체가 0이다"라는 테스트로 남는다
- 만족도 엔진은 결정적이다. 같은 입력에 같은 출력이 나오는 것을 테스트로 못 박는다 — 이것이 이 프로젝트의 핵심 주장이다
- LLM 판정처럼 비결정적인 것은 가짜 어댑터로 응답을 고정해 테스트한다

## 7. 코드 스타일

- **주석·독스트링·에러 메시지는 한국어. 식별자는 영어.**
- 모듈·함수·변수는 `snake_case`, 클래스는 `PascalCase`, 상수는 `UPPER_SNAKE`
- 공개 함수는 타입 힌트를 전부 단다. `Any`는 이유를 주석으로 적는다
- 주석은 "무엇"이 아니라 **"왜"**를 적는다. 코드가 말하는 것을 반복하지 않는다
- 한 파일이 400줄을 넘으면 분리를 검토한다

---

## 8. 품질 게이트

커밋 전에 전부 통과해야 한다.

```
ruff check . && ruff format --check .
mypy --strict src tests
lint-imports
pytest
```

`mypy --strict`다. 느슨한 층(`dict[str, ...]`)은 3-1의 의도적 타협이며, 그 외에는 예외를 두지 않는다.

## 9. 생성 이력 (provenance)

모든 LLM 호출은 `LlmPort` 한 곳을 지난다. 그 지점에서 다음을 JSONL로 남긴다.

```
out/provenance/<run_id>.jsonl
  ts · tier · model_id · instruction_hash · schema_name
  input_tokens · output_tokens · latency_ms · attempt · outcome
```

기성 관측성 도구를 포기한 대가를 이것으로 메운다. 동시에 이 로그가 「AI 활용 기술 문서」에 실을 실측 데이터가 된다 — 호출 수, 비용, 재생성률.

프롬프트 원문은 해시만 남기고 본문은 `out/provenance/prompts/`에 따로 둔다. 로그 파일이 프롬프트로 뒤덮이면 읽을 수 없게 된다.

## 10. 미확정 값 다루는 법

**게임 수치가 미확정이면 그럴듯한 값을 지어내지 않는다.**

- 확인이 가능하면 확인한다
- 진행을 위해 값이 필요하면 **가정값을 `data/project_bible.json` 한 곳에만** 넣고, 같은 파일의 `unconfirmed` 배열에 "무엇이 왜 미확정인지"를 함께 적는다
- 가정값을 코드나 프롬프트에 직접 쓰지 않는다. 그러면 확정 시점에 찾을 수 없다

## 11. 커밋

Conventional Commits의 변형을 쓴다. **작업 성격은 영어, 작업 내용은 한국어.**

```
<type>: <한국어 설명>
```

- **제목 한 줄. 50자 이내.** 한글도 1자로 센다
- 손으로 쓰는 커밋에는 본문을 쓰지 않는다. 필요할 만큼 커졌다면 커밋을 쪼갠다
- 마침표로 끝내지 않는다

| type | 쓰는 곳 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 동작 변화 없는 구조 변경 |
| `test` | 테스트 추가·수정 |
| `chore` | 의존성·설정·도구 등 그 외 |

```
feat: 만족도 엔진 곱셈 계산 구현
fix: 취향 이상 구간 경계값 오프바이원 수정
docs: 데이터 계약 버전 증가 규칙 추가
```

### 스쿼시 머지 커밋

roadmap 한 단계는 PR 하나로 묶여 **스쿼시 머지**된다 (머지 커밋·리베이스는 저장소 설정으로 막혀 있다).

- **PR 제목이 곧 스쿼시 커밋의 제목**이다. 따라서 PR 제목도 `<type>: <한국어 설명>` 형식으로 쓴다
- GitHub이 제목 뒤에 `(#N)`을 자동으로 붙인다. 끌 수 없으므로 **PR 제목은 45자 안쪽**으로 둬야 50자를 넘지 않는다
- **본문은 PR 바디가 그대로 들어간다.** 손으로 쓰는 커밋의 "본문 없음" 규칙에 대한 유일한 예외다

본문을 커밋 목록이 아니라 PR 바디로 두는 이유는, 저장소 문서를 자체 완결로 쓰는 것과 같은 논리다 — git 히스토리만 보고 "왜 이렇게 했나"가 읽혀야 한다. 무엇을 했는지는 diff가 말하지만, **판단의 근거는 남겨두지 않으면 복원되지 않는다.** 커밋 제목 목록은 PR 페이지에 그대로 남으므로 잃는 것이 없다.

따라서 **PR 바디는 영구 기록이라 생각하고 쓴다.**

- 템플릿의 `<!-- 주석 -->`을 지우지 않으면 그대로 커밋 메시지에 박힌다
- `Why`에는 코드를 읽어서 알 수 없는 것만 남긴다
- PR 템플릿은 `.github/pull_request_template.md`가 소유한다 (`What` / `Why` / `TBD`)

### 그 밖에

- 품질 게이트(8절)를 통과하지 않은 상태로 커밋하지 않는다
- 규약을 어기는 코드가 필요하면 코드가 아니라 이 문서를 먼저 고치고, 그 변경을 별도 커밋으로 남긴다
