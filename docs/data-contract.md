# 데이터 계약 — daily-special

> 파이프라인(Python)이 뱉고 서버(Spring Boot)·클라이언트(Unity)가 소비하는 **JSON 계약**.
> 세 저장소는 코드를 공유하지 않는다. **이 문서가 유일한 접점이다.**
>
> 이 문서는 자체 완결로 쓴다. 외부 문서를 참조하지 않는다.
> 최종 수정: 2026-07-30

---

## 0. 이 문서가 지금 존재하는 이유

서버도 클라이언트도 아직 없다. 그런데도 계약을 지금 정하는 이유는 둘이다.

1. **깨질 때 세 저장소가 동시에 깨지는 유일한 축이다.** 코드가 0줄인 지금이 가장 싼 시점이다.
2. **클라이언트의 착수 조건이다.** 계약이 확정되면 파이프라인이 실제 콘텐츠를 다 못 뽑았어도 클라는 손으로 쓴 목(mock) JSON으로 개발을 시작할 수 있다.

표기 규약·식별자·봉투 구조가 먼저 섰고, `guests.json`의 필드 구성은 만족도 엔진에서 역산해 7절에 확정했다. **네 파일이 모두 확정됐다** — 손님(7절) · 재료(8절) · 요리(9절) · 대사(10절).

## 1. 표기 규약

### 1-1. 키는 `snake_case`

```jsonc
{ "guest_id": "...", "ideal_ranges": { ... } }   // ✅
{ "guestId":  "...", "idealRanges":  { ... } }   // ❌
```

파이썬이 생산자이므로 생산자 쪽을 자연스럽게 둔다. 소비 측은 한 줄로 받는다.

- **Spring** — `spring.jackson.property-naming-strategy=SNAKE_CASE`, 또는 DTO에 `@JsonNaming(SnakeCaseStrategy.class)`
- **Unity** — `Newtonsoft.Json`의 `DefaultContractResolver { NamingStrategy = new SnakeCaseNamingStrategy() }`, 또는 필드마다 `[JsonProperty("guest_id")]`

### 1-2. 열거 값도 소문자 `snake_case`

```jsonc
{ "needs": ["restorative", "mild"] }
```

**단, 어휘 목록 자체는 이 문서가 소유하지 않는다.** 욕구 종류·요리 태그·식이 제약은 `data/project_bible.json`이 소유한다. 이 문서는 표기 형식만 정한다. 어휘가 늘어도 이 문서는 바뀌지 않는다.

### 1-3. 그 밖

| 대상 | 규약 |
|---|---|
| 시각 | ISO 8601 UTC 문자열 (`2026-07-25T06:00:00Z`) |
| 없는 값 | `null`을 쓴다. 키를 생략하지 않는다 — 소비 측이 오타와 구별할 수 없다 |
| 빈 목록 | `[]`. `null` 아님 |
| 소수 | JSON number. 문자열로 감싸지 않는다 |
| 인코딩 | UTF-8, 이스케이프 없이 한글 그대로 (`ensure_ascii=False`) |

## 2. 콘텐츠 ID

### 2-1. 의미 기반 슬러그를 쓴다. UUID를 쓰지 않는다

```
guest_ashen_scout_01
dish_herb_porridge
ingredient_river_herb
line_greet_gruff_03
```

문법: `<종류>_<의미>[_<일련번호>]`, `[a-z0-9_]`만 허용, 최대 64자.

종류 접두사는 다음으로 고정한다.

| 접두사 | 대상 |
|---|---|
| `guest_` | 손님 페르소나 |
| `dish_` | 요리 |
| `ingredient_` | 재료 |
| `line_` | 대사 |

**이유**: 이 ID를 서버 DB 컬럼과 클라 에셋 파일명이 물게 된다. 밸런스 로그·버그 리포트·에셋 폴더를 사람이 눈으로 읽어야 하고, `f47ac10b-58cc-...`는 그걸 못 한다. 개발 중 세 저장소를 오가며 같은 대상을 지목할 수단이기도 하다.

### 2-2. ID는 발행 후 불변이다

한 번 패키지에 나간 ID는 의미가 바뀌어도 재사용하지 않는다. 손님이 삭제되면 그 ID는 비워둔다. 서버 DB가 이미 그 ID로 관계·단골 기록을 들고 있다.

### 2-3. 대사 트리거는 의미 키로 참조한다

대사는 사람이 검수·수정한 결과물이라 비싸다. 게임 내부 상수나 DB PK에 결합하면 그 상수가 바뀔 때 검수 결과까지 버려진다.

```jsonc
// ❌ 내부 식별자에 결합 — 바뀌면 매칭 불가
{ "trigger_id": 1043 }

// ✅ 의미로 참조 — 나중에 매핑 한 장이면 붙는다
{ "situation": "dish_served_satisfied",
  "context": { "satisfaction_band": "high" } }
```

상위 설계가 확정되면 `의미 키 → 실제 상수` 매핑만 추가한다. 텍스트는 그대로 살아남는다.

## 3. 봉투 구조

모든 출력 파일은 같은 봉투를 쓴다.

```jsonc
{
  "schema_version": "1.0.0",
  "bible_version": "2026-07-25.1",
  "kind": "guests",
  "generated_at": "2026-07-25T06:00:00Z",
  "run_id": "run_20260725_0600",
  "items": [ /* ... */ ]
}
```

| 필드 | 의미 |
|---|---|
| `schema_version` | **이 계약의 버전.** semver. 소비 측이 호환성을 판단하는 기준 |
| `bible_version` | 이 산출물을 만든 `project_bible.json`의 버전. 밸런스 추적용 |
| `kind` | 파일 종류. 파일명과 중복되지만 파일이 옮겨져도 정체를 잃지 않게 한다 |
| `generated_at` | 생성 시각 |
| `run_id` | 생성 실행 식별자. `out/provenance/`의 로그와 이어진다 |
| `items` | 실제 내용 배열 |

### 3-1. `schema_version` 증가 규칙

| 변경 | 올리는 자리 |
|---|---|
| 필드 추가 (소비 측이 무시해도 동작) | patch |
| 필드 추가 (소비 측이 알아야 함) | minor |
| 필드 삭제·이름 변경·의미 변경·타입 변경 | **major** |

**major를 올리는 변경은 세 저장소가 함께 움직여야 한다.** 파이프라인 단독으로 올리지 않는다.

### 3-2. 소비 측 규칙

- **모르는 필드는 무시한다.** 파싱 실패로 다루지 않는다. 이래야 파이프라인이 minor를 혼자 올릴 수 있다
- **major가 다르면 로드를 거부하고 명시적으로 실패한다.** 조용히 넘어가면 밸런스가 어긋난 채로 굴러간다
- `bible_version`은 로그에만 쓴다. 이 값으로 분기하지 않는다

## 4. 출력 파일

`out/packages/<schema_version>/` 아래에 둔다.

| 파일 | `kind` | 내용 |
|---|---|---|
| `guests.json` | `guests` | 손님 페르소나 — 정체성·말투·취향 이상 구간·선호 욕구·식이 제약 (**7절에 확정**) |
| `dishes.json` | `dishes` | 요리 — 충족 욕구 태그·필요 재료·기본가 (**9절에 확정**) |
| `ingredients.json` | `ingredients` | 재료 — 신선/보존 구분·기본 시세·식이 저촉 (**8절에 확정**) |
| `lines.json` | `lines` | 대사 풀 — (상황 × 대상 × 말투) (**10절에 확정**) |

**`out/`을 git에 커밋한다.** 클라이언트가 API 키 없이 콘텐츠를 받으려면 파일이 저장소에 있어야 하고, 생성 결과의 변화가 diff로 보이는 것이 밸런스 작업에 직접 도움이 된다.

다만 아래 셋은 성격이 달라 다루는 법도 다르다.

### 4-1. 목 데이터와 산출물은 자리가 다르다

| 경로 | 무엇 |
|---|---|
| `out/packages/<schema_version>/` | **파이프라인이 생성한 것.** 매 실행마다 덮인다 |
| `out/mock/` | **손으로 쓴 것.** 계약이 어떻게 생겼는지 보여주는 표본 |

목을 지우지 않고 남기는 이유는 둘이다. 클라이언트가 생성 결과의 변덕에 흔들리지 않는 고정 표본을 가질 수 있고, **손으로 쓴 것과 생성된 것을 나란히 두고 비교할 수 있다.**

목 파일은 `run_id`가 `run_handwritten_mock_01`로 되어 있어 산출물과 헷갈리지 않는다.

### 4-2. 생성 이력은 **가려서** 커밋한다

`out/provenance/<run_id>.jsonl`에 호출 하나가 한 줄씩 남는다 — 티어·모델·토큰·지연·재시도·결과. 패키지의 `run_id`가 그 로그와 이어진다. 프롬프트 본문은 `out/provenance/prompts/`에 해시로 따로 둔다.

**규칙: 산출물을 만든 실행만 남기고 실험은 지운다.**

로그는 실행마다 파일이 하나씩 늘어난다. 스모크 테스트와 시행착오까지 그대로 두면 스무 번 돌린 뒤 열아홉 개가 노이즈이고, 그러면 아무도 읽지 않는다. 지금 `out/packages/`에 있는 것을 만든 실행만 남긴다 — 그 대응은 봉투의 `run_id`로 확인할 수 있다.

**실패한 실행이라도 산출물을 만들었으면 남긴다.** 검증 층이 무엇을 잡았는지가 그 로그에만 있고, 그것이 파이프라인이 일한다는 증거다.

저장소가 공개이므로 이 로그가 그대로 근거가 된다. 프롬프트 본문은 코드의 템플릿과 다르다 — 설정이 끼워 넣어진 **모델이 실제로 본 것**이라, 코드만으로는 재구성할 수 없다.

## 5. 계약에 넣지 않는 것

다음은 **파이프라인 산출물이 아니라 런타임 상태**다. 서버가 소유한다.

- 손님의 오늘 상태 (허기·컨디션·기분·지갑) — 매 방문 결정적으로 생성된다
- 플레이어와의 관계 수치, 단골 여부, 공개된 취향 정보
- 평판·소지금·재고

**경계 기준**: 플레이 중에 바뀌면 서버, 안 바뀌면 계약이다.

## 6. 이 계약을 바꾸는 절차

1. 이 문서를 먼저 고친다
2. `schema_version`을 3-1 규칙대로 올린다
3. major면 서버·클라 쪽에 필요한 변경을 함께 적는다
4. 그다음 코드를 고친다

코드를 먼저 고치고 문서를 나중에 맞추면, 세 저장소가 서로 다른 계약을 믿게 된다.

## 7. `guests.json` 항목

**확정 (`schema_version` 1.0.0).** 필드 구성은 취향이 아니라 **만족도 계산식이 무엇을 읽는가**에서 역산했다.

```jsonc
{
  "guest_id": "guest_ashen_scout_01",
  "name": "레하",
  "title": "잿빛 정찰병",
  "bio": "북쪽 능선을 훑고 돌아오는 장거리 정찰병. 사흘에 한 번 내려와 말없이 한 그릇을 비우고 간다.",
  "voice": "gruff",
  "personality": "칭찬을 아끼지만 맛있으면 그릇을 끝까지 비운다. 불평은 한 단어로 끝내고, 대신 다음에 또 온다.",
  "preferred_needs": ["filling", "restorative"],
  "ideal_ranges": {
    "heat":      { "low": 60, "high": 80 },
    "cook_time": { "low": 50, "high": 70 },
    "seasoning": { "low": 55, "high": 75 }
  },
  "dietary": []
}
```

| 필드 | 타입 | 읽는 쪽 | 의미 |
|---|---|---|---|
| `guest_id` | string | 서버 DB · 클라 에셋 | `guest_` 접두사 슬러그. 발행 후 불변 (2절) |
| `name` | string | 클라 UI | 한국어 표시명 |
| `title` | string | 클라 UI | 이름 옆에 붙는 짧은 정체성 |
| `bio` | string | 클라 UI | **무엇을 하는 사람인가.** 플레이어에게 보인다 |
| `voice` | string (어휘) | 런타임 대사 선택 | 말투 키. `lines.json`과의 **조인 키** |
| `personality` | string | 파이프라인(대사 생성) | **어떻게 말하고 반응하는가.** 런타임은 읽지 않는다 |
| `preferred_needs` | string[] (어휘) | 서버 | 평소 기우는 욕구. 가중치 없음 |
| `ideal_ranges` | { 축 키 → `{low, high}` } | 만족도 엔진 | 축별로 만족하는 구간 |
| `dietary` | string[] (어휘) | 만족도 엔진 | 식이 제약 키 |

"(어휘)"로 표시한 값은 `data/project_bible.json`이 소유한다. 목록이 늘어도 이 문서는 바뀌지 않는다 (1-2절).

### 7-1. `bio`와 `personality`를 나누는 이유

**소비자가 다르다.** `bio`는 클라이언트가 화면에 띄우고, `personality`는 대사 생성 프롬프트가 읽는다. 한 필드가 둘을 겸하면 UI에는 너무 길고 프롬프트에는 정보가 없는 글이 나온다. 같은 이유로 `personality`는 런타임에 필요 없다 — 대사는 이미 생성돼 `lines.json`에 있다.

### 7-2. `ideal_ranges`에 없는 축은 "취향 없음"이다

1-3절의 "없는 값은 `null`, 키를 생략하지 않는다"는 **필드**에 대한 규칙이고, `ideal_ranges`는 맵이라 **키 집합 자체가 정보**다. 축이 빠져 있으면 그 축은 어떤 값이든 만족한다는 뜻이며, 만족도 계산에서 아예 채점되지 않는다. 모든 축을 채우고 취향 없음을 `null`로 표현하면 소비 측이 "아직 안 정해진 것"과 구별할 수 없다.

### 7-3. 말투는 왜 자유 텍스트가 아닌가

대사 풀이 `(상황 × 말투)`로 짜여 있어 `voice`가 조인 키다. 자유 텍스트면 런타임이 대사를 한 줄도 고를 수 없다. 손님마다의 결은 `personality` 문장이 따로 나른다 — **조인은 키가, 결은 문장이 맡는다.**

### 7-4. 여기 없는 것

`preferred_needs`는 "평소 성향"이고, **이번 방문의 욕구가 아니다.** 오늘의 욕구·허기·컨디션·기분·지갑은 매 방문 달라지므로 서버가 소유한다 (5절). 손님의 지갑이 빠듯하다는 사실은 계약에 담을 수 없고, `preferred_needs`에 `affordable`이 들어가는 것으로 나타난다.

## 8. `ingredients.json` 항목

**확정.** 요리가 참조하는 대상이자 **식이 저촉의 출발점**이다.

```jsonc
{
  "ingredient_id": "ingredient_boar_shank",
  "name": "멧돼지 정강이",
  "kind": "fresh",
  "description": "질기지만 오래 고면 국물이 진해지는 부위. 든든한 한 그릇의 바탕이 된다.",
  "base_price": 7,
  "dietary_conflicts": ["no_meat"]
}
```

| 필드 | 타입 | 읽는 쪽 | 의미 |
|---|---|---|---|
| `ingredient_id` | string | 서버 DB · 클라 에셋 | `ingredient_` 접두사 슬러그. 발행 후 불변 (2절) |
| `name` | string | 클라 UI | 한국어 표시명 |
| `kind` | `fresh` \| `preserved` | 서버 · 클라 | 신선은 그날 소멸, 보존은 재고 유지 |
| `description` | string | 파이프라인(요리 생성) · 클라 UI | 어떤 재료이고 어떤 맛인지 |
| `base_price` | int | 서버 | 기준 단가. 그날 시세의 중심값 |
| `dietary_conflicts` | string[] (어휘) | 서버 | 이 재료를 쓴 요리가 저촉하는 식이 제약 |

### 8-1. 식이 저촉은 재료가 나른다

만족도 엔진은 `dish.dietary_conflicts`를 **결과로만** 받는다. 그 결과를 만드는 것이 여기다 — **요리의 저촉 = 쓴 재료들의 저촉 합집합.**

태그(`meat`/`dairy`/…)를 달고 태그 → 제약 매핑을 따로 두지 않는다. 매핑이 하나 더 생기면 어휘가 늘 때마다 두 곳을 고쳐야 한다 (욕구와 요리 태그를 같은 어휘로 둔 것과 같은 이유).

### 8-2. `kind`는 게임의 경제 축이다

메뉴 두 층이 여기 얹혀 있다 — 신선은 **오늘의 메뉴**를 떠받치며 장보기를 도박으로 만들고, 보존은 **상시 메뉴**의 약속 비용이 된다. **한 종류만 있는 패키지는 유효하지 않다.** 어느 쪽이 없어도 게임의 한 층이 통째로 죽는다.

### 8-3. 여기 없는 것

오늘 시장에 무엇이 나왔는지, 오늘 얼마인지, 창고에 몇 개 있는지는 **런타임 상태**라 서버가 소유한다 (5절). `base_price`는 서버가 흔들 기준선이다.

## 9. `dishes.json` 항목

**확정.** 다른 생성물(재료)을 참조하는 유일한 항목이다.

```jsonc
{
  "dish_id": "dish_boar_bone_stew",
  "name": "멧돼지 뼈국",
  "description": "정강이를 오래 고아 국물을 낸 뜨끈한 국. 하루를 걸어온 사람의 다리를 풀어 준다.",
  "need_tags": ["filling", "restorative"],
  "ingredient_ids": ["ingredient_boar_shank", "ingredient_barley_grain"],
  "base_price": 14
}
```

| 필드 | 타입 | 읽는 쪽 | 의미 |
|---|---|---|---|
| `dish_id` | string | 서버 DB · 클라 에셋 | `dish_` 접두사 슬러그. 발행 후 불변 (2절) |
| `name` | string | 클라 UI | 한국어 표시명 |
| `description` | string | 클라 UI · 파이프라인(대사 생성) | 어떤 요리인지 |
| `need_tags` | string[] (어휘) | 만족도 엔진 | 이 요리가 답하는 욕구 |
| `ingredient_ids` | string[] | 서버 | 필요한 재료. **`ingredients.json`에 실재해야 한다** |
| `base_price` | int | 만족도 엔진 | 고정가. 플레이어가 정하지 않는다 |

### 9-1. 여기 **없는** 것 세 가지는 전부 유도된다

| 없는 것 | 어디서 나오나 |
|---|---|
| `dietary_conflicts` | 쓴 재료들의 저촉 **합집합** |
| 상시/오늘의 메뉴 구분 | 신선 재료가 하나라도 있으면 오늘의 메뉴로만 가능 |
| 파라미터 3축 | 요리의 속성이 아니다 — 플레이어가 매번 맞추는 값이다 |

**저장하면 어긋난다.** 재료의 저촉을 고쳤는데 요리가 옛 값을 들고 있으면, 아무도 모르는 채 육류 불가 손님에게 고기가 나간다.

파라미터가 여기 없는 것은 더 중요하다. **요리 선택이 욕구에 답하고 파라미터가 취향에 답하는 두 축 분리**가 설계의 핵심이라(design.md 3장), 한쪽이 다른 쪽으로 새면 게임이 무너진다.

### 9-2. 원가는 판매가보다 낮아야 한다

`base_price`는 쓴 재료들의 `base_price` 합보다 커야 한다. 계약이 강제하지는 못하지만 파이프라인 검증이 ERROR로 막는다 — 재료를 모르면 볼 수 없는 검사라, 안 하면 만들수록 손해인 요리가 밸런스 시뮬레이션까지 살아남는다.

### 9-3. 소비 측이 알아야 할 것

`ingredient_ids`는 **패키지 사이의 참조**다. `dishes.json`을 읽는 쪽은 `ingredients.json`도 함께 읽어야 하고, 둘의 `bible_version`이 같은지 확인하는 편이 안전하다.

## 10. `lines.json` 항목

**확정.** 대사 풀은 **상황 × 대상 × 말투**로 짜인다.

```jsonc
{ "line_id": "line_order_restorative_gruff_01",
  "situation": "order",
  "subject": "restorative",
  "voice": "gruff",
  "text": "순찰길이 길었어. 뜨끈한 걸로." }
```

| 필드 | 타입 | 읽는 쪽 | 의미 |
|---|---|---|---|
| `line_id` | string | 서버 DB | `line_` 접두사 슬러그. 발행 후 불변 (2절) |
| `situation` | string (어휘) | 런타임 | 언제 나오는 대사인가 |
| `subject` | string (어휘) \| `null` | 런타임 | 이 대사가 가리키는 대상 |
| `voice` | string (어휘) | 런타임 | 말투. 손님의 `voice`와 잇는 **조인 키** |
| `text` | string | 클라 UI | 대사 본문 |

### 10-1. 왜 축이 셋인가

설계 초안은 `(상황 × 말투)` 둘이었는데 그것으로는 정보 공개 곡선의 두 대사를 만들 수 없다.

```
"속이 쓰려요"   상황(주문)은 같은데 어느 욕구인지가 대사를 정한다
"좀 짠데요"     상황(피드백)은 같은데 어느 축이 어긋났는지가 대사를 정한다
```

대상 축이 없으면 손님은 "뭔가 아쉽네요"밖에 말하지 못하고, **플레이어가 좁힐 것이 없어 취향 추론이 성립하지 않는다.**

### 10-2. `subject`가 무엇을 가리키는지는 상황이 정한다

상황 어휘(`project_bible.json`)가 각자 `subject` 종류를 선언한다 — `need` / `axis` / `none`.

| situation | subject | 조합 |
|---|---|---|
| `greet` · `reaction_high` · `reaction_low` · `leave` | `none` | 말투 수 |
| `order` | 욕구 | 말투 × 욕구 |
| `feedback_high` · `feedback_low` | 파라미터 축 | 말투 × 축 |

상황 어휘를 `order_restorative`처럼 미리 펼치지 않는다. 그러면 욕구 어휘가 상황 목록에 복제되어, 욕구를 하나 늘릴 때 상황도 함께 늘려야 한다.

`subject`는 **한 가지 의미만 갖는다** — "이 대사가 가리키는 대상". 상황마다 필드를 따로 두면(`need`, `axis`, …) 대부분이 늘 비어 있고, 어느 것이 채워져야 하는지를 소비 측이 다시 판단해야 한다.

### 10-3. 빈 자리는 런타임의 침묵이다

한 조합에 대사가 하나도 없으면 **그 자리에서 손님이 입을 다문다.** 파싱은 성공하고 테스트도 통과하므로, 최종 패키지를 낼 때 커버리지를 반드시 확인한다 (9단계).

같은 조합에 여러 줄을 두고 런타임이 그중 하나를 고른다. 한 줄뿐이면 같은 손님이 매번 똑같은 말을 한다.

### 10-4. 게임 내부 상수에 결합하지 않는다

2-3절의 규칙이 여기 적용된 것이다. `situation`·`subject`·`voice` 전부 의미 키이고, 게임 상수가 바뀌어도 `의미 키 → 상수` 매핑 한 장이면 붙는다. 대사는 사람이 검수한 결과물이라 비싸고, 상수가 바뀔 때 그것까지 버려지면 안 된다.

## 11. 아직 정하지 않은 것

**계약의 네 파일이 전부 확정됐다.** 남은 것은 하나뿐이다.

- 재료의 시세 변동 폭 — 런타임이라 서버 소유지만, 폭이 크면 계약의 `base_price`가 무의미해진다

**여기 있는 항목에 그럴듯한 값을 지어 넣지 않는다.** 진행에 값이 필요하면 `data/project_bible.json`에 가정값으로 넣고 같은 파일의 `unconfirmed` 배열에 근거를 남긴다.
