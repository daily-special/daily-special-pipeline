# 오늘의 정식 (Daily Special) — 게임 설계서

> `daily-special` · 모험가 길드의 가성비 구내식당을 운영하는 코지 경영 시뮬
> 최종 수정: 2026-07-25

## 0. 문서의 목적

NAN 2026 (NHN 게임×AI 해커톤) 출품작의 설계서다. **혼자, 18일**(마감 8/10) 조건에서 만든다.

이 문서는 대회 예선 제출물인 **게임 소개서**와 **AI 활용 기술 문서**의 초안을 겸한다. "무엇을 만드는가"뿐 아니라 **"AI를 어디에 어떻게 썼는가"**를 명시한다.

## 1. 컨셉

**모험가 길드의 구내식당을 운영하며, 찾아오는 모험가(손님)의 그날 사정과 취향을 알아내 요리로 만족시키고, 길드가 믿고 찾는 가성비 밥집으로 키우는 경영 시뮬레이션.**

### 핵심 재미

```
누가 올지 모른 채 재료를 산다        ← 도박
손님이 온다. 상태에서 나온 욕구를 표현한다  ← 관찰
가진 재료로 최선을 만든다            ← 타협
반응을 보고 취향을 배운다            ← 축적
```

조합이 수단, 관계가 목적이다. **관계 = 정보 = 실력.** 손님과 친해질수록 취향을 알게 되고, 그게 곧 더 잘 만들 수 있는 능력이 된다.

### 톤과 레퍼런스

- 라이트 판타지, 코지(cozy), **도트** 기반
- 육성 사이클: 우마무스메 / 느긋한 축적: 동물의 숲·스타듀 밸리 / 가벼운 조작: 블루 아카이브·트릭컬
- **조작 숙련이 아니라 추론·관찰·축적**이 재미의 축

## 2. 핵심 루프 / 세션 구조

**하루가 한 판이다.**

```
아침 — 장보기    오늘의 시장에 재료가 뜬다. 예산 한정. 누가 올지 모른 채 산다.
낮  — 영업       손님이 한 명씩 온다. 대화 → 파악 → 요리 → 반응.
밤  — 마감·정산  돈·평판·관계 갱신. 단골이 정보를 흘린다.
```

- 한 손님 30초~1분, 하루 5~8명 → **한 세션 5~10분**
- 실시간 압박 없음

## 3. 요리·주문 시스템

### 주문 모델 = C (상황 요청)

손님은 **요리를 지정하지 않는다.** 그날 상태에서 나온 **욕구**를 표현한다.

> *"던전에서 데여서 속이 쓰려요."*

플레이어의 실력은 네 층이다.

1. 손님의 상태를 읽는다
2. 그 욕구에 맞는 요리를 **메뉴에서 고른다**
3. 손님 취향에 맞게 **파라미터를 잡는다**
4. 애초에 그런 손님을 만족시킬 **메뉴를 갖춰뒀는가**

이 모델이 핵심 재미(숨은 취향 추론)를 살리고, 손님을 진짜 에이전트로 만든다 — 손님이 "요리 X"를 짚으면 에이전트가 하는 일이 없지만, "내 상태에 맞는 걸 원한다"는 상태에서 나온 판단이다.

### 요리 = 정체성 + 품질 두 층

```
재료 + 조리법  →  어떤 요리인가       (유한. 사전 정의/생성)
파라미터       →  얼마나 잘 만들었나  (연속. 플레이어 실력)
```

- **파라미터 3축**: 불 세기 / 조리 시간 / 간. 슬라이더 3개
- 요리 선택은 **욕구**에 답하고, 파라미터는 **취향**에 답한다 (두 축 분리)

### 노가다 방지 (정답 암기를 막는 장치)

1. **재료 제약** — 정답을 알아도 오늘 산 재료로는 못 만든다 → 차선 찾기
2. **손님 간 자원 충돌** — 둘이 같은 재료를 원하는데 하나뿐이면 누굴 만족시킬지 고른다
3. **손님 상태 변동** — 취향을 알아도 오늘 컨디션에 따라 흔들린다

미니게임은 최하 우선순위(남으면).

---

## 4. 메뉴 (두 층)

### 상시 메뉴 — 전략층 (식당의 정체성)

- 늘 제공하겠다고 약속한 요리 몇 개
- **누가 오는지를 결정한다.** 매운 요리를 상시로 두면 매운 걸 원하는 모험가가 모인다 → 평판·단골층과 직결
- **보존 재료**를 안정적으로 확보해야 함 (경제적 약속)
- 천천히 바뀜. "나는 어떤 식당인가"

### 오늘의 메뉴 — 전술층 (장보기 도박의 보상)

- 오늘 장본 **신선 재료**로만 가능한 한정 요리
- 특별 손님이나 프리미엄 취향에 대응. 매일 바뀜 → 매일 다른 판단

재료 이분(신선/보존)이 메뉴 두 층을 경제적으로 구별한다 (→ 6장).

## 5. 손님 = 하이브리드 에이전트 + 만족도 엔진 (AI 코어) ⭐

이 게임의 심장이자 대회 승부처. 곧 제출물 **에이전트 설계서**의 알맹이다.

### 왜 하이브리드인가

- **순수 온라인 에이전트**(매 상호작용 LLM 추론)는 비용·지연·통제가 문제. 게임 루프에 못 넣는다
- **순수 콘텐츠 생성**만 하면 "에이전트"가 사라진다. 대회는 에이전트를 요구한다
- 그 사이가 **하이브리드** — 진짜 에이전트인데 런타임 추론이 0

### 구조

```
[오프라인, LLM]   페르소나 생성 = 정체성 · 말투 · 행동 파라미터
        ↓ 컴파일
[인게임, 결정적]  손님이 페르소나 + 오늘 상태로
                  → 욕구를 표현하고 → 내 요리를 평가하고 → 반응한다
                  LLM 호출 없음. 빠르고, 재현되고, 테스트 가능
[대사]            반응 대사는 (상황 × 대상 × 말투) 풀에서 사전 생성 → 런타임 선택
[기억·관계]       손님이 나에 대해 아는 것 · 단골도 = DB 상태
```

지각(메뉴·요리) → 결정(욕구·평가) → 행동(반응·팁·재방문) → 기억(관계). **에이전트 루프가 온전하다.** 정책이 LLM 호출이 아니라 컴파일된 결정적 함수일 뿐.

### 만족도 엔진

**손님이 갖는 것**

- **페르소나 (고정, 숨겨짐 → 관계로 공개)**: 취향(불/시간/간 3축의 이상 구간), 선호 욕구 카테고리, 식이 제약. 여기에 정체성과 말투가 함께 실리는데 그쪽은 만족도 계산이 아니라 화면과 대사가 쓴다
- **오늘 상태 (매 방문 생성, 결정적)**: 허기 · 컨디션(정상/부상/피로) · 기분(우울/평온/들뜸) · 지갑

> 페르소나의 정확한 필드 목록은 데이터 계약이 소유한다(`data-contract.md` 7절). 계산에 쓰이는 것은 이상 구간과 식이 제약 둘뿐이고, 나머지는 클라이언트 UI와 대사 생성기가 읽는다.

**상태 → 욕구**

상태가 이번 방문의 **우선 욕구 1~2개**를 낳는다. 욕구 어휘는 요리 태그와 같은 말을 쓴다.

```
포만 · 회복 · 순한 · 자극 · 저렴 · 특별   (6종)

예:  부상 + 피로  →  회복 + 순한
     지갑 부족     →  저렴
     축제 기분     →  특별 + 포만
```

욕구 2개는 충돌할 수 있다 — "회복 + 저렴"(회복식은 비싼데 돈이 없다)처럼.

**만족도 계산 — 네 항 전부 곱셈, 결과는 항상 0~1**

```
만족 = 욕구 충족도   (고른 요리가 이번 욕구를 얼마나 커버?)
     × 취향 일치도   (파라미터가 이상 구간에 얼마나 가까운가)
     × 예산 적합     (이 지갑으로 감당되나)
     × 식이 계수     (제약을 어겼나)

만족 → 팁(돈) · 평판 · 관계(정보 공개)
```

곱셈인 이유: 하나라도 0에 가까우면 전체가 낮아진다. "요리는 맞는데 취향이 어긋나면" 반쯤만 만족. 덧셈이면 한쪽만 잘해도 통과해버린다.

**식이 위반을 뺄셈이 아니라 곱셈 계수로 둔다.** 뺄셈 항이 하나 섞이면 결과가 음수가 될 수 있어 clamp가 필요해지고, clamp는 "얼마나 나빴나"를 뭉갠다. 또 앞 세 항이 0~1 비율인데 뺄셈 항만 절대량이라 값을 정할 근거가 없다. 계수로 두면 위반이 둘일 때 자연히 더 낮아지고, 결과가 항상 0~1에 머문다. 게임 감각으로도 맞다 — 육류 불가 손님에게 고기를 내는 것은 "좀 아쉬움"이 아니라 못 먹음이다.

**각 항의 정의**

| 항 | 계산 | 결정 근거 |
|---|---|---|
| **욕구 충족도** | 오늘의 욕구 중 요리 태그가 덮은 비율. 단 **바닥값** 아래로 내려가지 않는다 | 욕구가 1개인 손님은 비율이 0/1 이분법이 되어, 빗나가면 아무리 잘 만들어도 만족 0이 된다. 하드 게임오버 없음 기조와 어긋나므로 바닥을 둔다 — "원하던 건 아니지만 밥은 먹었다" |
| **취향 일치도** | 축별로 이상 구간 안이면 1.0, 밖은 허용 오차까지 선형 감소, 넘으면 0. **세 축은 평균** | 축 간에도 곱하면 감쇠가 6중첩된다. 세 축이 각각 0.7일 때 곱은 0.34, 평균은 0.7 — 곱셈이면 웬만큼 잘 만들어도 바닥이라 개선이 체감되지 않는다. 취향 일치도는 "얼마나 잘 만들었나" 하나의 값이므로 축 사이는 평균이 맞다 |
| **예산 적합** | 가격 ≤ 지갑이면 1.0, 넘으면 선형 감소해 지갑의 N배에서 0 | 이분법이면 1원 차이로 만족이 통째로 0이 되어 곱셈 구조에서 지나치게 가혹하다. **비율만 쓰므로 화폐의 절대 스케일이 필요 없다** |
| **식이 계수** | 위반 없으면 1.0, 위반 하나당 계수를 곱한다 | 위 참조 |

수치(바닥값·허용 오차·예산 배수·위반 계수)는 코드에 박지 않는다. **ProjectBible이 소유**하고 밸런스 시뮬레이션으로 조정한다.

**욕구 2개의 가중치는 동등하다.** 손님은 "속이 쓰려요" 한 마디를 할 뿐이라 어느 욕구가 더 중요한지 플레이어가 알 방법이 없다. 알 수 없는 것으로 점수를 가르면 추론이 아니라 운이 된다. 관계가 깊어져 "이분은 회복을 제일 중요하게 봐요"가 공개되는 시점에 가중치로 승격시킬 수 있다.

**`저렴` 욕구와 예산 적합은 다른 것을 잰다.** 태그는 **요리의 속성**(손님이 바뀌어도 안 바뀐다), 예산은 **손님과 요리의 관계**(손님마다 다르다)다. 같은 국밥이 빈털터리에게도 원정대장에게도 `저렴` 태그지만, 예산 적합은 서로 다르다. 둘이 함께 낮아지는 경우("회복 + 저렴" 손님에게 비싼 회복식)는 설계가 의도한 욕구 충돌이 제대로 아픈 것이다.

**결과는 단일 숫자가 아니라 항별 점수를 함께 낸다.** 정보 공개 곡선의 "좀 짠데요"가 축별 점수에서 나오고, 밸런스 시뮬레이션이 어느 항이 병목인지 봐야 하며, 런타임 이식본이 파이썬 레퍼런스와 정확히 같은지 항별로 대조할 수 있어야 한다.

### 정보 공개 곡선 (관계 = 정보)

```
첫 방문   욕구 힌트만 ("속이 쓰려요") → 취향은 추측
피드백    "좀 짠데요" → 취향 축 하나가 좁혀짐
단골      취향 구간 · 식이 제약 공개 → 확실히 맞출 수 있음
```

### 대사 풀은 두 축이 아니라 세 축이다

위 두 대사가 그 이유다. **상황과 말투만으로는 만들 수 없다.**

```
"속이 쓰려요"   상황(주문)은 같은데 어느 욕구인지가 대사를 정한다
"좀 짠데요"     상황(피드백)은 같은데 어느 축이 어긋났는지가 대사를 정한다
```

그래서 대사는 **상황 × 대상 × 말투**로 짜인다. "대상"은 이 대사가 가리키는 것이고, **무엇을 가리키는지는 상황이 정한다** — 주문 대사의 대상은 욕구, 피드백 대사의 대상은 파라미터 축, 인사 대사는 대상이 없다.

상황 어휘를 `주문_회복`처럼 미리 펼치지 않는다. 그러면 욕구 어휘가 상황 목록에 복제되어, 욕구를 하나 늘릴 때 상황도 함께 늘려야 한다.

정보 공개 곡선이 이 층에 얹혀 있다. 대상 축이 없으면 손님은 "뭔가 아쉽네요"밖에 말하지 못하고, **플레이어가 좁힐 것이 없어 취향 추론이 성립하지 않는다.**

### 온라인 추론 다이얼

- **기본 = 0** (풀 선택)
- **선택 = 하루 마감 리뷰 한 곳**에만 예산. 지연은 "생각 중…" 연출로 흡수. 시연용. 여유 시 추가

### 디렉팅 (제출물 "디렉팅 명세서"의 실체)

플레이어는 손님을 **명령할 수 없다.** 환경·메뉴·가격·재료 구성으로만 **간접 영향**을 준다.

## 6. 경제

### 자원 4종

- **돈** — 재료 구매·설비 투자
- **재료** — 장보기로 획득, 요리에 소비
- **평판** — 만족 누적. 다음날 손님 유입을 결정
- **관계** — 손님별. 정보 공개

### 하루 흐름

```
아침  예산으로 재료를 산다. 시장은 매일 재료·가격이 다르다
낮   손님 응대. 요리마다 재료 소비. 만족 → 팁 + 평판 + 관계
밤   정산. 남은 재료 처리, 평판 반영
다음날 평판이 손님 수·질을 결정
```

### ⭐ 재료 이분 (메뉴 두 층과 맞물림)

| | 소멸 | 연결 | 경제적 의미 |
|---|---|---|---|
| **신선 재료** | 그날 안 쓰면 상함 | 오늘의 메뉴 | 장보기 도박. 과잉 구매 = 손해 |
| **보존 재료** | 재고 유지 | 상시 메뉴 | 늘 확보 = 예산 압박 |

신선 재료의 소멸이 장보기 도박을 살린다. 보존 재료는 상시 메뉴의 약속 비용.

### 가격 = 고정가

요리별 고정 기본가. 만족도의 "예산 적합"은 손님 지갑 vs 고정가로 판정.
(플레이어 가격 설정은 여유 시 성장 요소로 올릴 수 있음)

### 고정비 = 평소 약함 + 목표날 압박

임대료 등 소액이 평소 나가되 부담 없고, "이번 주 길드 납품" 같은 **목표 있는 날**에만 조여온다. → 혼합 긴장과 정합.

---

## 7. 평판 = 빕구르망 가성비 등급

파인다이닝(별점)이 아니라 **구내식당의 가성비**가 축이다. 미슐랭의 별이 아니라 **빕구르망 철학**을 차용한다.

### 가성비 사다리

```
무명 식당 → 길드 게시판 등재 → 길드 추천점 → 원정대 보급 지정
```

- 평가 기준 = **예산 안에서 얼마나 잘 먹였나**. 비싸게 파는 게 아니라 한정된 지갑의 모험가를 만족시키는 것
- 등급이 오르면: 손님이 **많아지고 유명해진다**(부유해지는 게 아니라). 돈은 **물량 + 효율(설비)**에서 나온다 → 고정가 경제와 정합, 구내식당 컨셉 유지

### 암행 감식관 (미식 모험가 / 길드 감식관)

```
평가 기간이 열린다 (현재 등급에서 충분히 잘하면 열림. 알림 옴)
   → 감식관이 일반 손님 사이에 섞여 온다. 누군지 모른다
   → 예산 안에서 잘 먹였나를 종합 평가 → 등급 획득/유지/강등
```

효과 네 가지:

1. 평가 기간에만 긴장 → 혼합 긴장과 정합
2. 누가 감식관인지 모르니 **모든 손님을 잘 대접해야 함** → 관계 축과 시너지
3. 감식관 = 특별 손님 에이전트 → **에이전트 시스템 쇼케이스**
4. 시연 영상 골드 — *"이 남루한 모험가가 길드 감식관이었다"*

- **익명성 = 약한 힌트**: 설비·성장으로 "오늘 감식관이 왔을 수도" 정도의 신호. 긴장과 공정함의 타협
- **강등 완화**: 별을 잃는 건 드물게, 회복 가능하게. 하드 게임오버 없음 유지

## 8. 성장 · 수집 · 관계

### 성장 2축

- **주축 — 손님 정보·관계**: 단골이 늘고 취향이 공개됨. 관계=정보=실력
- **보조축 — 식당 설비**: 재료 슬롯 확장, 파라미터 정밀도·범위, 좌석 수 → 더 많은 손님 감당

### 수집 = 단골 명단 (가챠 아님)

- **긴 꼬리** — 뜨내기 손님 다수 (AI 에이전트, 얕음, 게임의 변주)
- **단골** — 잘 대접해 마음을 연 소수 → 취향 완전 공개 + 사연 해금 + 애착. **이게 수집 로스터**
- 단골 명단이 차오르는 게 수집의 쾌감. **뽑는 게 아니라 길러서 얻는다**

**가챠 없음** (대회 스코프). 획득 = 평판이 오르면 손님이 찾아옴. discovery가 살아 있음(취향을 모른 채 만남). 가챠의 "새 캐릭터!" 도파민은 "새 모험가가 들어왔다"가 대신함.

> **획득(어떻게 얻나)을 컬렉션·관계(얻은 뒤 뭘 하나)와 분리**해둔다. 그러면 상용화 시 가챠는 "획득 방식 하나"로 싸게 슬롯인된다. 단 **지금 가챠 대비 훅을 미리 심지 않는다** — 깨끗한 분리는 공짜지만 투기적 훅은 비용이다.

### 관계 → 에피소드 (가볍게)

- 관계 마일스톤에서 **사연·에피소드 해금** (호감도작 → 해금의 맛)
- **가볍게**: 한 줄~짧은 사연 수준. 여러 장면짜리 스토리 아님. AI 생성
- 에피소드 해금이 취향 정보 공개도 겸함 → **감정 + 유틸 이중 보상**

### 간판 캐릭터 앵커 = 조수/동료 하나

- 같이 식당을 꾸리는 조수. **늘 곁에 있는** 손으로 쓴 고정 캐릭터 (뽑는 로스터 아님)
- 역할: **게임의 얼굴 · 튜토리얼 목소리 · 마일스톤 반응 · 감정 앵커**
- 터치포인트: 1일차 튜토리얼 / 초반 아침 팁 / 첫 순간들(첫 손님·첫 단골·첫 별·감식관) / 등급 상승 축하
- 관계 아크·연애 루트 없음. 초상화 하나 + 대사 수십 줄
- **길드 역할(평판·목표 납품)은 캐릭터가 아니라 게시판/알림 UI**로 — 앵커를 온기 하나에 집중, 캐릭터 하나로 유지
- 우선순위 낮게 (폴리시 단계)

## 9. 긴장과 실패 (혼합)

- **평소**: 느긋. 하드 게임오버 없음. 동숲·스타듀 결
- **목표 있는 날**: 길드 납품, 축제, 감식관 평가 기간. 긴장이 생기고 실패 시 평판·돈 타격
- 느긋함과 긴장이 번갈아 오는 리듬

## 10. AI 활용 전체 (제출물 핵심)

| 층 | 무엇 | 런타임 추론 | 상태 |
|---|---|---|---|
| 1. 오프라인 콘텐츠 생성 | 손님·요리·재료·대사 생성·검증 | 0 | 파이프라인 재사용 |
| 2. 하이브리드 손님 에이전트 | 페르소나 → 결정적 정책 | 0 (+선택 1곳) | **코어** |
| 3. 밸런스 시뮬레이션 | 에이전트끼리 플레이해 경제 검증 | 0 (오프라인) | 선택 |

**서사**: AI로 콘텐츠를 만들고(1) → 게임 안에서 에이전트로 작동하며(2) → 에이전트끼리 플레이시켜 밸런스를 검증한다(3). 하나의 파이프라인.

**차별점**: 대부분의 참가자는 손님마다 매 턴 LLM을 부를 것이다. 우리는 LLM이 생성한 페르소나를 **결정적 정책으로 컴파일**해 추가 추론 비용을 0으로 만든다. 게임 회사는 수백만 명에게 서비스한다 — 비용·지연·재현성을 통제한 설계가 어필 포인트다.

## 13. 기술 구성

| 영역 | 기술 | 비고 |
|---|---|---|
| 콘텐츠 파이프라인 | Python | `vtuber-ip-copilot` 패턴 재사용. ProjectBible → 술집/식당 도메인으로 교체 |
| 게임 서버 | Spring Boot | 계정 · 컬렉션 영속화 · 비동기 아레나 · 평판 · 저장/불러오기 |
| 클라이언트 | Unity (도트 2D) | **1~2일차 APK 스파이크 후 확정**. 막히면 웹(Phaser/React + Capacitor) |
| 아트 | 도트 = 무료 에셋 팩 / 2D 초상화 = AI 생성 | 컷씬 애니메이션(Live2D)은 최하 우선순위 |
| 플랫폼 | Android (맥 없어 iOS 불가) | 에뮬레이터로 테스트 |

### 저장소 레이아웃 (물리 분리, 3 repo) — **확정**

```
daily-special-pipeline    Python AI 콘텐츠 생성   (우분투) ← 이 repo. 여기 docs/도 있음
daily-special-server      Spring Boot 런타임      (우분투, 배포 대상) — 서버 작업 시작 때 생성
daily-special-client      Unity 도트 2D          (윈도우) — 스파이크로 Unity 확정 후 생성
```

- **AI 파이프라인을 별도 repo로 물리 분리한다.** 콘텐츠를 생성해 **데이터로 뱉고**(손님 페르소나·요리·재료·대사) 서버·클라가 소비. 코드 공유 없이 **데이터 계약(스키마)으로만** 만난다. 파이프라인이 대회의 AI 쇼케이스라 「AI 활용 기술 문서」가 여기 붙는다
- **개발 배치**: 파이프라인·서버는 우분투(서버는 배포 대상이라 리눅스 개발), 클라는 윈도우. 서버↔클라는 개발 중 LAN(별도 머신 2대). 초반 클라는 목 데이터로 개발 후 통합
- `vtuber-ip-copilot`은 건드리지 않는다 — 친구와의 미래 게임용. **패턴만 복사**해 온다 (ProjectBible이 도메인 데이터 소유 · OpenAI structured outputs · 검증→재생성 · 런타임 LLM 0)

## 14. 18일 일정 (척추 우선, 어디서 끊어도 제출 가능)

```
1~2일   Unity APK 스파이크 (go/no-go) + 파이프라인 식당 도메인 교체
3~6일   싱글 척추 — 하루 사이클 · 장보기 · 손님 1명 · 상황 요청 · 파라미터 요리 · 반응
        ↑ 여기까지만 돌아도 "게임 + 영상"이 나온다
7~9일   손님 에이전트 — 여러 명, 욕구·취향·상태 변동, 관계=정보 성장, 만족도 엔진
        ↑ 대회 AI 핵심. 척추보다 먼저 튼튼히 해도 됨
10~12일 Spring 서버 — 계정 · 컬렉션 · 저장/불러오기 + 평판(빕구르망)·감식관
13~14일 비동기 멀티 — 단골 방문 · 평판 전파   ← 백엔드 쇼케이스
15일    식당 설비 (2번째 성장 축) · 메뉴 편성
16~17일 아트 통합 · 목표 있는 날(혼합 긴장) · 폴리시
18일    빌드 · 시연 영상 · 게임 소개서 · AI 활용 기술 문서 (+버퍼)
```

**끊는 선**: 6일차=게임, 9일차=AI 게임, 14일차=백엔드까지 있는 게임. 어디서 멈춰도 제출물.
**주의**: AI 활용 기술 문서를 18일차에 몰지 않는다. 만들면서 쌓는다 (기존 ADR 3편이 상당 부분 커버).

## 15. 미정 / 리스크

- **Unity 스파이크 go/no-go** — 1~2일차. 실패 시 웹 전환
- **요리 이미지 처리** — 도트 아이콘 조합 vs 생성. 요리 종류가 많으면 이미지 비용 폭발
- **세계관 디테일** — 길드·모험가 설정 톤, 게임 정식 명칭
- **밸런스 수치** — 재료비·손님 수·욕구 분포. 단순하게 시작해 시뮬로 검증
- **경제 밸런싱**이 타이쿤 최대 함정. 한 곳만 틀려도 무너지거나 너무 쉬워진다
